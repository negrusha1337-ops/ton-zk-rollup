## Что это

Первый ZK-rollup с EVM на TON. Конечная цель: EVM-блоки исполняются в Reth, доказываются zkVM
(SP1 или RISC Zero), доказательство сворачивается в Groth16 на BLS12-381 и проверяется
rollup-контрактом на TON L1 (state root, депозиты, выводы по Merkle-доказательству, escape hatch).

Репозиторий сейчас содержит только **этап 0 — спайк осуществимости**: работает ли проверка
Groth16 (BLS12-381) в TVM и сколько она стоит. Ответ: работает, дёшево. Детали — `REPORT.md`.

- **Публичные значения батча — восемь слов (256 байт)**:
  `chainId ‖ prevStateRoot ‖ newStateRoot ‖ batchHash ‖ prevWithdrawalsRoot ‖ withdrawalsRoot ‖ prevDepositHash ‖ newDepositHash`.
  Из сообщения — только новый корень состояния и новый корень выводов; остальное контракт
  берёт из хранилища. Выхода — пять слов: `chainId ‖ stateRoot ‖ l2Account ‖ amount ‖ recipientHash`.
- **У ключа rollup'а один переменный вход — дайджест.** Нонс SP1 равен нулю и свёрнут в IC0;
  поля `nonce` в `SubmitBatch`/`ForceExit` нет; `FinalizeKey` отказывает ключу со второй
  таблицей. Причина: таблицу для нонса не задействовал бы ни один пруф — проверить её нечем.
- **Плата за место в очереди L1** удваивается на каждые 64 элемента окна (между отметками
  target и head) и сбрасывается принятым батчем; жёсткого предела нет намеренно. У депозита
  поле `maxFee` (иначе комиссия молча уменьшила бы сумму на L2); текущие значения — get-метод
  `queueFees`. Суммы депозитов сценария зашиты в пруфы и возможны только по базовой комиссии.
- **Принудительные транзакции L2**: `ForceTransaction` ставит подписанную транзакцию (одна
  ячейка без ссылок, до 127 байт, плата от 0,05 TON) в очередь L1; в очередь идёт хеш ячейки,
  ПЕРЕСОБРАННОЙ из её битов (иначе ссылка на библиотеку ломает очередь). Программа zkVM
  обрабатывает очередь по порядку (`QueueItem` в `zkvm/lib`); некорректную транзакцию — и
  принудительную, и из данных секвенсора — ПРОПУСКАЕТ.
- **Аварийный выход** (`contracts/rollup/escape.tolk`): элемент очереди L1 ждёт дольше
  `escapeTimeout` (не меньше часа — иначе ключи не фиксируются) → кто угодно замораживает
  rollup → счета L2 выходят по пруфу программы выхода (`zkvm/exit-lib`, `zkvm/exit-program`),
  необработанные депозиты возвращаются по квитанциям. Согласие на выход подписывается под
  `chainId`, корень состояния и получателя.
- **Выплата не теряется**: нуллификатор помечает заявку до выплаты, поэтому шаг выплаты либо
  платит, либо записывает долг (`RollupState.owed`, сообщение `PayOwed`). Пороги монет
  (`withdrawMinValue`, `forceExitMinValue`, `nullifierMinValue`) считаются из газа по ценам сети.
- `contracts/rollup_mock.tolk` — двойник с заглушкой проверки пруфа, ТОЛЬКО для тестов логики.
  Отличается от настоящего одной строкой: все проверки до пруфа — в общих функциях
  `prepareSubmitBatch` / `prepareForceExit`.
- Программы zkVM: `zkvm/` (Rust; `lib` — логика батчей, `exit-lib` — выход, `program` и
  `exit-program` — гости SP1, `native` — сценарий и запуск без zkVM). Игрушечный реестр, не EVM,
  но с настоящими подписями: счета как в Ethereum (secp256k1, адрес — keccak от ключа),
  отправитель восстанавливается из подписи, у счёта есть nonce (`zkvm/lib/src/tx.rs`).
  `zkvm/script` (хост с `sp1-sdk`, вне workspace) исполняет программы в zkVM, считает их
  ключи и строит Groth16-пруфы — `PROVING.md`.

  второй депозит → батч 2 → батч 3; аварийные выходы — из состояния после батча 3. Батч 3

## Команды

```bash
npx blueprint test          # все тесты (Circom не нужен, фикстуры в репозитории)
npm run zk:build            # пересобрать схемы, setup и доказательства (нужен Circom)
npm run zk:verifiers        # перегенерировать Tolk-верификаторы из fixtures/
npm run zk:network-config   # обновить снимок цен газа mainnet
npm run zk:cost-report      # таблица «газ → TON» из измерений
cd zkvm && cargo test -p rollup-stf -p rollup-exit -p rollup-native && cargo run -p rollup-native   # программы zkVM нативно
cd zkvm/script && ./target/release/rollup-script --batch 2 --execute   # исполнение в zkVM без пруфа (сборка — PROVING.md)
cd zkvm/script && ./target/release/rollup-script --vkeys               # ключи программ → fixtures/zkvm_batches/program.json
node zk/gen-rollup-key.mjs             # ключ контракта из исходников → fixtures/zkvm_batches/key.json
npx blueprint run verifyRollupDeployment --testnet --mnemonic <адрес> <chainId> <мин. срок, с> <корень генезиса>   # сверка развёрнутого контракта
npx blueprint run runRollupTestnet --testnet --mnemonic escape   # вернуть депозит, если обычный путь прогона встал
node zk/gen-evm-exit-fixture.mjs       # фикстура выхода счёта EVM (anvil в .tools/foundry; меняет файл целиком)
python3 zk/evm-exit-mutation-check.py  # мутации evm_exit.tolk: каждая обязана быть убита своим тестом
```

После `zk:build` обязательно `zk:verifiers`, затем тесты: ключи и доказательства должны быть
из одной сборки.

## Структура

- `circuits/` — схемы Circom. `build/` не коммитится.
- `zk/` — скрипты сборки (`circuits.mjs` — реестр схем).
- `fixtures/<схема>/` — ключ верификации, доказательство, публичные сигналы. Коммитятся.
- `contracts/generated/` — вывод `export-ton-verifier`. **Руками не править.**
- `contracts/hashed_inputs_verifier.tolk` — вариант с одним публичным входом (SHA-256).
- `contracts/rollup/` — хранилище, сообщения и логика rollup-контракта (см. `ARCHITECTURE.md`);
  `wrappers/rollupMath.ts` и `zk/gen-rollup-batches.mjs` повторяют его арифметику вне цепочки —
  все три обязаны совпадать.
- `contracts/bn254/` — программное спаривание BN254; `constants.tolk` генерируется
  `node zk/gen-bn254-constants.mjs`, эталонные векторы — `node zk/gen-bn254-vectors.mjs`,
  константы ключа, свидетель и подсказки — `node zk/gen-bn254-groth16-fixture.mjs [имя фикстуры]`;
  импорт пруфов из файлов zkVM — `node zk/import-sp1-fixture.mjs`, `node zk/import-risc0-fixture.mjs`
  (ссылки на исходные файлы — в `source.json` фикстур); набор разных пруфов — `node zk/gen-bn254-cases.mjs`.
- `bench/gas-results/` — пишется тестами; `bench/network-config.json` — снимок конфига сети.

## Что нужно помнить

- **Пруфы SP1 строить только по команде пользователя** и только после независимой враждебной
  проверки изменений (отдельные агенты-рецензенты на модели Fable, тест на каждую найденную
  атаку, повторная проверка без критичных находок). Собственные тесты и совпадение газа в
  testnet проверкой безопасности не считаются. Причина: 13.11.2026 такая проверка нашла две
  критичные дыры в коде, уже прошедшем testnet (см. `REVIEW.md`). То же — для коммита и
  заливки кода, меняющего протокол.
- **После любого изменения `zkvm/lib`, `zkvm/exit-lib` или гостевых программ**: пересобрать
  `zkvm/script`, `--vkeys`, `zkvm/script/verify-elf.sh` (чистая пересборка ELF и сверка с
  `program.json` — обязательна перед пруфами), `node zk/gen-rollup-key.mjs` и `--check`.
  Если ELF изменился — прежние пруфы негодны: удалить `fixtures/sp1_rollup_*` и `proof-*.json`.
  Если изменились только тесты (ELF прежний) — пруфы годны. `program.json` и `key.json`
  руками не править. После правки `zkvm/native` — `cargo run -p rollup-native` и пересборка скрипта.
- **Не ставить `SP1_SKIP_PROGRAM_BUILD`** при сборке `zkvm/script`: с ней в бинарник попал бы
  прежний ELF. Сборка теперь отказывает, но правило то же для любых «ускорений» сборки гостей.
- **Тест на отказ по неверному пруфу обязан ждать код 7300** и использовать «лучшую подделку»
  (честные подсказки для ложного утверждения: `forgery` в `fixtures/rollup_batches/batches.json`,
  `statementForgery` в фикстурах SP1). Пруф с чужими подсказками падает раньше, с кодом 7006, и
  замыкающее равенство не проверяет.
- **Тест обязан ломаться от поломки защиты.** Третий круг проверял тесты мутациями и нашёл
  выжившие: защита есть, тест «на неё» проходит и без неё. Новый тест на защиту проверять так
  же: убрать проверку в коде и убедиться, что тест упал. Пороги и константы брать у контракта
  (get-методы), а не копировать в тест; сценарные значения не должны быть нулевыми там, где
  ноль скрывает ошибку (так прежние корни в батчах 1–2 скрывали бы их отсутствие в байтах).
- **Двойник (`rollup_mock.tolk`) не доказывает ничего про проверку пруфа.** Всё, что касается
  пруфа, ключей и газа, проверять на настоящем контракте (`tests/RollupProof.spec.ts`,
  `tests/RollupKeys.spec.ts`). Два файла точки входа обязаны совпадать построчно, кроме двух
  строк проверки пруфа: за этим следит `tests/MockParity.spec.ts`.
- Отрицательные тесты — с точным кодом отказа, не `success: false`.
- Замеры в `bench/` тесты пишут через `saveGasReport`: файл не трогается, если набор не
  собрал все измерения.

- **Blueprint зафиксирован на 0.46.0.** Версия 0.47 убрала Tolk, а сам Blueprint объявлен
  устаревшим в пользу Acton. Не обновлять `@ton/blueprint` без миграции на Acton.
- **256-битное значение не помещается в публичный вход**: поле BLS12-381 ~255 бит. Корни
  хешируются в один вход `sha256(...) mod 2^253`.
- **Четыре `uint256` не помещаются в одну ячейку** (1024 > 1023 бит).
- **Проверку нельзя запускать из external-сообщения** до `accept_message`: кредит 10 000 gas.
- Sandbox 0.45 эмулирует global version 15, сеть на 17. Для верификатора BN254 и
  для rollup-контракта (батчи, депозит, вывод) расход в testnet совпал с Sandbox до единицы.
- В `contracts/bn254/` нельзя использовать `MULADDDIVMOD`: частное не помещается в 257 бит
  на нередуцированных входах (исключение 4). Только `MULMOD`; инвариант границ — в `fp2.tolk`.
- Большие функции Tolk помечать `@inline_ref`: без пометки компилятор зависает на встраивании,
  а `@noinline` даёт вызов через словарь кода за ~190 gas против 56 у `@inline_ref`.
- В `hinted.tolk` нельзя менять порядок хеширования транскрипта: на нём держится корректность.
- `HINT_CHECKPOINT_EVERY`, `HINT_WINDOW_BITS` и `HINT_BIGQ_CELLS` в `hinted.tolk` должны
  совпадать с `CHECKPOINT_EVERY`, `WINDOW_BITS` и `BIG_Q_COEFFICIENTS / 4` в `zk/bn254-hints.mjs`.
- Ключ с оконными таблицами (тысячи ячеек) загружается в контракт частями по ≤ 23 КБ и
  затем фиксируется; раскладка дерева в `windowTable`/`assembleTable` (`zk/bn254-hints.mjs`)
  и в контракте обязана совпадать, иначе разойдётся хеш ключа в транскрипте.
- Скрипты `scripts/*.ts` работают только с `--testnet --mnemonic` (`wrappers/testnetGuard.ts`):
  `--custom-type testnet` выдаёт за testnet любой API, а TON Connect подписывает в своей сети.
  Мнемоника — только в `.env` пользователя, в репозиторий не попадает.
- **Мак пользователя — 16 ГБ. Тяжёлое (jest, cargo, сборки) запускать строго по одному**, под
  `nice`, jest с `--maxWorkers=2`; агентов с правом запуска — по одному, параллельно только
  читающих. 13.11.2026 четыре агента с тестами разом повесили машину.
- Выплату по балансу получателя сверять с допуском: сеть удерживает с получателя его плату
  за хранение (в прогоне 13.11.2026 — 89 нанотон, скрипт «не дождался» дошедшей выплаты).
- Blueprint в фоне с `< /dev/null` завершается ошибкой `readline was closed` уже ПОСЛЕ
  сценария: смотреть на строку «Готово», а не на код выхода.
- В скриптах «нуллификатор развёрнут» ≠ «заявка погашена»: развернуть его может кто угодно.
  Смотреть `isClaimed` (`wrappers/RollupNullifier.ts`) и факт выплаты либо долг (`owedPayout`).
- Газ мерить на полноразмерном публичном входе (253 бита): на маленьком он занижен на ~0,2 млн.
- Trusted setup в `zk/build.mjs` — одноучастниковый, только для тестов.
- Цифры газа не выдумывать: только из Sandbox (`bench/gas-results/`) или из конфига сети.
- Никаких приватных ключей и мнемоник в репозитории. Только Sandbox и testnet.
- SDK SP1 6.10.0 строит пруфы под схему v6.1.0, а фикстура `sp1_v6_fibonacci` — v6.0.0: ключи
  верификатора разные. Нонс SP1 (пятый вход) задаёт доказывающий; `zkvm/script` фиксирует 0.
- `zkvm/script` собирается только с `protoc` (переменная `PROTOC`, бинарник в `.tools/protoc`).
- Groth16 на ноутбуке с 16 ГБ: пиковый след 29–32,5 ГБ, всё держится на подкачке; 8–9 минут
  на пруф. Запускать только через `zkvm/script/prove-polite.sh` (ждёт затишья, низкий
  приоритет, пауза на время чужой тяжёлой работы; внутри — сторож диска `prove-guarded.sh`),
  по одному, при 20+ ГБ свободного места; перед пруфами — `verify-elf.sh`. Сборка —
  `--features native-gnark` с Go из `.tools/go`.
- Ключ программы (`programVKey`) зависит от точного ELF и входит в IC0 ключа контракта.
  Сборка программ идёт строго по `zkvm/Cargo.lock` (`locked`), но побайтно не воспроизводима
  (нет Docker): на другой машине ключ может получиться другим.
- Монеты, приложенные к сообщениям сверх газа, остаются на контракте, а вывести их нечем:
  суммы для testnet — только из `wrappers/rollupValues.ts` (около 2× измеренного расхода;
  тесты на настоящем контракте шлют те же суммы в Sandbox).
- Раскладка порции данных в ячейки (127 байт на ячейку, ячейка i → ячейки 4i+1…4i+4) — часть
  протокола: `dataChunkCell` (`wrappers/rollupMath.ts`), её копия в `zk/gen-rollup-batches.mjs`
  и `data_chunk_hash` (`zkvm/lib`) обязаны совпадать. Цепочкой ячеек порцию не делать:
  эмулятор Sandbox падает на глубине под 500.
- В `zkvm/Cargo.toml` крейты `sha2`, `sha3` и `k256` заменены версиями с прекомпиляциями SP1
  (теги под версию SP1): без них хеш данных в zkVM в 5,5 раза дороже, а подпись — на порядки.
  При смене версии SP1 менять и теги. Подписанный перевод стоит около 39 тыс. циклов.
- Публичные значения — восемь слов (256 байт). Четыре `uint256` в ячейку не помещаются,
  поэтому дайджест в контракте считается из трёх строителей (3 + 3 + 2 слова).
- Замеры циклов по меткам — сборка `zkvm/script` с `--features profiling` в отдельный каталог
  (`--target-dir target/profiling`); прувер собирать без этой опции.
- Groth16 на этом ноутбуке при параллельной нагрузке идёт 14 минут и доходит до порога сторожа
  (4 ГБ свободного места): перед запуском закрывать всё тяжёлое.
- В скриптах testnet после каждой отправки ждать подтверждения по состоянию контракта
  (`waitFor`), а не по таймеру, и не глушить ошибки отправки: иначе следующее сообщение уйдёт
  раньше предыдущего. Так уже был потерян `SetExitKey` в прогоне 13.11.2026.
- Ключ программы выхода = ключ программы батчей с другим IC0; контракт собирает его сам
  (`exitVkData`). Порядок развёртывания: части ключа → `SetExitKey` → сверка ключа выхода →
  `FinalizeKey` → сверка развёртывания (`wrappers/rollupDeployment.ts`).
- **Комментарий в шапке `zkvm-evm/lib/src/lib.rs` «нет аварийного выхода для состояния EVM»
  устарел, но править его нельзя** (9-Д): сдвиг строк может изменить ELF программы EVM, её
  ключ и сделать негодным пруф `fixtures/sp1_evm_batch2`. Поправить при плановой смене программы.
- Не менять `zkvm/lib` без нужды: от него зависит ELF обеих программ (выхода — тоже, она
  использует типы и хеши из `zkvm/lib`), а с ним их ключи и все пруфы: пять пруфов, больше часа.
  В ELF программы батчей есть номера строк исходников (места паник): даже правка комментария,
  сдвигающая строки в `zkvm/lib/src/lib.rs`, `data.rs` или `zkvm/program/src/main.rs`, меняет
  ELF и ключ. Тесты (`tests.rs`) и сценарий (`zkvm/native`) на ELF не влияют.
- Изменение кода контракта пруфы НЕ ломает: они привязаны к `chainId`, а не к адресу.
- Circom ставится локально: `cargo install --git https://github.com/iden3/circom.git --tag v2.2.3 --root .tools circom`
  (или переменная `CIRCOM_BIN`).
