# sequencer/ — сборщик блоков L2 как сервис (этап 2, шаги 1–2)

Сервис читает очередь L1 контракта, собирает блоки EVM на локальном узле reth v2.2.0, проверяет
каждый блок **программой батча** (нативный расчёт хоста `zkvm-evm`) до того, как блок станет
проверенной вершиной, и отдаёт батч пруверу и отправщику. Протокол не меняется: программа,
контракт и ключи — те же (`PROTOCOL-V2.md`). Прувер — `LocalProver` (SP1 Groth16 на этой машине,
`prover.ts`), заготовка `RemoteProver` (сервер с GPU, `remoteProver.ts`) и `MockProver` для
двойника; отправщик — `TestnetSubmitter` (testnet, `submitter.ts`) и `SandboxSubmitter`. В testnet
сервис ещё не запускался (см. «Чего нет»).

## Как запустить

Бинарники вне репозитория (`PROVING.md`): `.tools/reth/bin/reth` (v2.2.0),
`.tools/rsp/target/release/rsp`, `zkvm-evm/target/release/rollup-evm-host`.

```bash
# Полный цикл на настоящем узле Reth и двойнике контракта в Sandbox (8 блоков, перезапуски узла,
# подменённые ответы узла и хоста); каталог — .tools/sequencer-test/, не каталог сервиса:
npx jest --runInBand tests/SequencerReth.spec.ts
# Узел не нужен: чистые функции, сверки, ветки сервиса на заглушках узла и хоста, очередь из
# записанных страниц toncenter, отправщик на двойнике и на настоящем контракте с пруфом SP1:
npx jest --runInBand tests/SequencerUnits.spec.ts tests/SequencerChecks.spec.ts tests/SequencerService.spec.ts \
  tests/SequencerQueue.spec.ts tests/SequencerSubmitter.spec.ts
# Правки круга 20, прувер на заглушке сторожа, отправщик testnet на настоящем контракте в Sandbox:
npx jest --runInBand tests/SequencerRound20.spec.ts tests/SequencerProver.spec.ts tests/SequencerTestnet.spec.ts
# Очередь L1 контракта в testnet — только чтение, без ключей (TONCENTER_API_KEY — по желанию):
npx ts-node sequencer/main.ts queue <адрес контракта> [--from=<номер>] [--max=<число>]
# Сервис против контракта в testnet (раздел ниже): сначала check, затем run.
npx ts-node sequencer/main.ts check <адрес контракта> --fee-recipient=0x…
npx ts-node sequencer/main.ts run <адрес контракта> --fee-recipient=0x…
```

Сервис как библиотека: `startNode` (`node.ts`) поднимает узел с генезисом протокола, `Sequencer`
(`service.ts`) получает конфигурацию и зависимости и продвигается вызовами `step()`; пример —
`tests/SequencerReth.spec.ts`. Демона с циклом и отправщиком для сети нет (см. «Чего нет»).

## Конфигурация (`SequencerConfig`)

| Поле | Что |
|---|---|
| `chainId` | идентификатор rollup'а; сервис сверяет его с узлом, контракт — с подписями |
| `feeRecipient` | получатель чаевых — адрес секвенсора на L2 (единственное свободное поле заголовка) |
| `stateDir` | каталог состояния, по умолчанию `.tools/sequencer/` (`DEFAULT_STATE_DIR`) |
| `rpcUrl`, `genesisPath` | HTTP JSON-RPC узла и его генезис — для rsp |
| `includePool` | брать транзакции секвенсора из пула узла |
| `tools` | пути к хосту и rsp; `executeInZkvm` — ещё и исполнение в zkVM без пруфа; `timeoutMs` — предел времени запуска (по умолчанию 10 мин, с zkVM — 30) |
| `maxBatchQueueItems` | предел отрезка — **get-метод `queueLimits` контракта**, не копия |
| `maxBlockAge` | срок приёма батча после времени блока — **get-метод `deployment` контракта**; при старте сервис сверяет его (и `chainId`) с контрактом, расхождение — отказ |
| `programKeysPath` | `fixtures/evm_batches/program.json` (по умолчанию): с ним сверяется сборка хоста |
| `staleCandidateAge` | кандидат старше этого после перезапуска собирается заново; по умолчанию `maxBlockAge / 4` |
| `submitMargin` | запас до конца срока приёма перед отправкой (перед пруфом — сверх времени пруфа), с; по умолчанию 300 |
| `expectedProofTime` | ожидаемое время пруфа, с; по умолчанию 1800 |
| `expectedCheckTime` | ожидаемое время проверки кандидата (rsp, хост, сверки), с; по умолчанию 300. Условие запуска: `expectedCheckTime + expectedProofTime + submitMargin < maxBlockAge`, иначе отказ (с наименьшим `maxBlockAge` контракта, 1800, значения по умолчанию не проходят) |
| `rebuildMargin` | запас после конца срока приёма, с; по умолчанию 60: батч, который мог уйти контракту, пересобирается, только если снимок контракта позже `срок + rebuildMargin` и батча в нём нет |
| `queueLagLimit` | сколько терпеть отставание источника сообщений очереди (`QueueLagError`), с; по умолчанию 1800, дальше — остановка |
| `clockSkewLimit` | наибольшее расхождение часов машины со временем L1 при старте, с; по умолчанию 60 |
| `poolGasBudget` | бюджет газа транзакций пула на блок; по умолчанию 5 млн (`DEFAULT_POOL_GAS_BUDGET`) |
| `toolRetries` | повторы хоста и rsp после сбоя инструмента; по умолчанию 2 |

Зависимости (`SequencerDeps`): узел (`NodeRpc`), источник очереди (`QueueSource`), прувер
(`Prover`; `cancel` — отменить задание пересобранного блока), отправщик (`BatchSubmitter`;
`contractState` — номер и корень последнего принятого батча **и время блока L1, на котором это
прочитано**; `deployment` — параметры развёртывания), время L1 (`l1Now` — время последнего блока TON: в
Sandbox `blockchain.now`, в сети — `sync_utime` провайдера в снимке счёта rollup'а). Узел слушает только 127.0.0.1; секрет Engine
API — новый на каждый запуск, лежит в каталоге узла (права 600, и при перезаписи).

**Пул наружу не открывать.** Транзакции пула ограничены только газом (`poolGasBudget`), а цена
газа для прувера не ограничена (принцип 0.1 PROTOCOL-V2.md: `blake2f` — порядка 10⁹ циклов на
транзакцию). Пока нет бюджета циклов на блок, пул — только для транзакций самого секвенсора;
открыть его пользователям значит отдать любому выключатель rollup'а (блок, который не доказать
за срок). **Наружу окончательный только `finalized`** (блок, батч которого принял контракт).
`safe` — блок, проверенный программой: при пересборке (батч не успел в окно `maxBlockAge`) он
**откатывается** на родителя и заменяется соседом той же высоты, так что транзакции в нём не
окончательны. `latest` — тем более: отвергнутый программой кандидат остаётся временной головой
узла до следующего кандидата той же высоты.

**При старте** сервис: берёт каталог состояния (`sequencer.lock`, `lock.ts`: файл с pid, именем
машины и токеном появляется сразу целиком — `link` временного файла, отказ, если файл есть;
«моя ли блокировка» — только по токену, pid в контейнере у всех 1; чужой токен и живой pid — занят,
другая машина — занят, файл без содержимого моложе 10 с — занят, иначе мёртв; мёртвая снимается
переименованием в уникальное имя со сверкой содержимого — чужая живая, снятая в гонке, возвращается
`link`; свою снимает только со сверкой токена); сверяет хост с `program.json` (`rollup-evm-host --identity`: хеш ELF, хеши исходников
программы при сборке и на диске, исходники хоста при сборке и на диске) — устаревший хост
останавливает сервис до пересборки; сверяет часы машины со временем L1. Отчёт хоста о каждом
блоке тоже сверяется с `program.json` (`programElfSha256`, `sourcesSha256`).

## Что делает

**Очередь L1** (`queue/`). Контракт хранит об элементе только хеш цепочки до него; получатель
депозита и байты принудительной транзакции есть только во входящих сообщениях. Источник
читает отметки и хеши get-методами (`depositQueue`, `queueItem`, `depositReceipt`), элементы —
из сообщений `DepositTon`/`ForceTransaction` успешных транзакций контракта в порядке lt, и
принимает элемент №n, только если `sha256(хеш до n ‖ …)` равен хешу после n у контракта.
Расхождение — `QueueMismatchError` с номером элемента и транзакцией, не пропуск. Сумма депозита —
из квитанции. Реализации: Sandbox — перехваченные результаты отправок (`SandboxFeed.record`);
testnet — toncenter v3 `/transactions?account=…&start_lt=…&sort=asc` и get-методы через
toncenter v2 (`TonClient`), с ограничением частоты и повтором на 429. Курсор — сообщение
последнего элемента проверенного блока; без курсора счёт идёт с начала истории контракта.

**Сборка блока** (`block/`, `service.ts`), для каждого блока:

1. отрезок `(N₀, N]` — префикс очереди после вершины, не длиннее `queueLimits`, не дальше головы.
   Принудительную транзакцию от счёта, которому в этом же отрезке зачисляется депозит, программа
   пропускает (зачисления — в конце блока, правка 0.4); это законный исход. Правка 0.4 советует
   честному сборщику резать отрезок перед ней, но безусловная обрезка — рычаг на пропускную
   способность (очередь D(X) F(X) D(X) F(X)… давала бы по два элемента на блок, круг 18, H2).
   Поэтому отрезок режется, только если очередь не длиннее предела **и** предыдущий блок так не
   резался (`tip.cut`): под нагрузкой блок всегда полный, без неё — каждый второй;
2. форма принудительных — **у программы**: `rollup-evm-host --classify-forced` вызывает
   `decode_forced_transaction` из `zkvm-evm/lib` (правила `forced.rs` на TypeScript не
   переписаны). Мусор и негодные подписи до узла не доходят;
3. зачисления: депозиты отрезка, номер — место в блоке **с нуля**, валидатор — 0, сумма < 2⁶⁴;
4. `testing_buildBlockV1`: принудительные первыми в порядке очереди, затем пул (по флагу; фильтр —
   типы 0/1/2, свой `chainId`, без блобов и EIP-7702); время `max(родитель + 1, сейчас)`,
   `prevRandao` и корень beacon-блока — ноль;
5. сверка ответа: принудительные — ровно запрошенные, байт в байт; пул — подпоследовательность;
   родитель, время, получатель чаевых, зачисления, лимит газа 30 млн, пустой `extraData`, ноль
   blob-газа. Узел (skip-invalid по умолчанию) выбрасывает негодную транзакцию и все следующие
   того же отправителя молча: первая выброшенная у каждого отправителя убирается, состав
   собирается снова, пока ответ не совпадёт с запросом;
6. `engine_newPayloadV3` (VALID) → временная голова (см. ниже) → вход блока штатным rsp
   (`debug_executionWitness`) → доказательства счетов отправителей годных по форме
   принудительных (`eth_getProof` на родителе) → **хост нативно** с `--previous-report`;
7. собственный расчёт сервиса против отчёта программы: сначала несущие слова отдельно
   (`newStateRoot` — хеш кандидата, `prevStateRoot` — хеш проверенной вершины), затем 11 слов (хеш
   очереди — по своей очереди, дерево выводов — по логам моста в квитанциях узла, функции
   `wrappers/rollupMath.ts`), отметки очереди, фронтир, байты публичных значений; данные батча —
   `debug_getRawBlock` узла; судьба принудительных — **по порядку**, не по множеству байтов (две
   одинаковые в одном отрезке законны: копию чужой ставит кто угодно, программа включает первую
   и пропускает вторую): i-я запись отчёта — о i-й принудительной отрезка с её местом
   (`queueIndex`), каждая включённая — следующая транзакция блока байт в байт, других
   принудительных в блоке нет;
8. только теперь блок **проверен**: safe узла, вершина сервиса, каталог `blocks/<N>/`
   (`payload.json`, `report.json`, `batch.bin` — вход батча, `job.json` — задание пруверу).

Отвергнутый программой кандидат вершину не двигает: причина — в журнале и в
`state.json` (`rejections`), вторая попытка — без транзакций пула; отвергнут и он — остановка
(`SequencerStop`). Расхождение расчёта сервиса с программой — сразу остановка.

Отказ программы — это ровно паника хоста на `process_evm_batch` (код 101 и строка «нативный
расчёт отверг батч»). Всё прочее — сбой инструмента: код 2 (несогласованный свидетель — ошибка
самого сервиса), другая паника, сигнал (предел времени, OOM), сбой rsp. Сбой повторяется
(`toolRetries`), а не записывает кандидата в отвергнутые; повторы кончились — остановка, кандидат
остаётся в работе со своей фазой. Хост и rsp запускаются под `nice` с пределом времени и стоят
на учёте (`children.ts`): при выходе процесса их гасят SIGKILL, а по сигналу (SIGINT, SIGTERM,
SIGHUP) — SIGTERM и до 15 с на завершение (reth сбрасывает базу), затем SIGKILL.

**Пруф и батч.** Следующий шаг после проверки — `Prover.prove(job)` и `BatchSubmitter.submit`.
Задание ключуется хешем блока и sha256 его публичных значений (`jobKeyOf`); пруф несёт ключ своего
задания, и сервис отказывает пруфу с чужим ключом (и после пруфа, и пруфу с диска) до отправки.
`jobKey` — **метка** задания (каталог очереди, отказ перепутанному пруфу), а не защита: прувер
мог бы написать любую. Привязку пруфа к батчу дают сверка его публичных значений с блоком при
импорте (`proofImport.ts`) и сам контракт: он проверяет пруф под своим ключом на публичном входе,
собранном из своего хранилища, — чужой пруф там не пройдёт, какую бы метку он ни нёс. Отправщик идемпотентен (принятый батч и опубликованные данные не
повторяются, частично опубликованные сбрасываются) и до отправки сверяет публичный вход,
который соберёт контракт (`expectedPublicInput`), с 11 словами программы. После приёма —
finalized узла.

**Срок приёма и пересборка** (0.3: контракт берёт батч, пока `время блока ≤ время L1 ≤ время блока +
maxBlockAge`; решение — чистые функции `deadline.ts`). Порядок шага с непринятым батчем: время L1 →
**контракт** (`contractState`, со временем снимка `utime`): принят этим блоком — записать и сдвинуть
finalized, без проверки срока (сервис мог упасть между приёмом и записью; точка сбоя `submitted`);
принят другим блоком или контракт ушёл дальше блока сервиса — остановка. Два времени: `seen` — время
снимка «не принят», `fresh = max(l1Now, seen)`. У toncenter за балансировщиком свежий сервер может
ответить временем, а отстающий — состоянием (круг 20, 1): «не принят» верно только на `seen`. Дальше:
- до пруфа: `время блока + maxBlockAge < fresh + expectedProofTime + submitMargin` → пересборка;
- блок из будущего L1 (`время блока > fresh`, 7329) → шаг `waiting`, не остановка;
- до отправки: `… < fresh + submitMargin` → пересборка, если батч не уходил; если мог уйти
  (`submitting` записан до отправки) — `waiting`, пока `срок + rebuildMargin < seen` не станет верно
  (сообщение в пути может попасть в блок на самой границе), затем пересборка.

Пересборка: задание пруверу отменяется (`Prover.cancel`), каталог блока уходит в
`blocks/<N>.stale-<хеш>`, вершина — назад на родителя (он же последний принятый: конвейера нет),
`safe` узла — назад на родителя (голова та же), `state.rebuild` держит прежний отрезок. Блок той же
высоты собирается со свежим временем из **того же отрезка** (сверяется с контрактом: обработанное —
отметка родителя, элементы — те же; предел и голова от этого не нарушаются), транзакции пула —
заново, собирается и пустым. Новый кандидат — сосед прежнего: reth переводит на него и голову, и
`safe` (проверено: `forkchoiceUpdated` с safe на соседа той же высоты — VALID, safe сменился).
Пересборка, прерванная сбоем в любой точке (после отмены, записи, переименования, отвода safe),
доводится при старте идемпотентно (`rebuild.ts`): каталог прежнего блока (хеш в `payload.json` —
`rebuild.replaces`) уходит в сторону, если ещё на месте; safe узла — назад на вершину.

**Блокировка и сигналы** (круг 20, 9). Владение блокировкой перепроверяется перед каждой записью
состояния и перед отправкой батча (`assertHeld`): чужая блокировка — `StateDirBusy`, ни записи, ни
отправки. Обработчик сигналов стоит на каждый сигнал: первый — SIGTERM дочерним и ожидание, второй —
SIGKILL и выход сразу (блокировка снимается обработчиком выхода); с первого сигнала новые
инструменты не запускаются (и повторы после сбоя — тоже, `ShuttingDown`). Отправщик testnet
перепроверяет блокировку перед **каждым** сообщением (круг 21, 5в), не только перед батчем.

**Дочерние процессы** (круг 21, 3 и 4). Окружение каждого запуска — `childEnv()`: без
`WALLET_MNEMONIC`, `SEQUENCER_MNEMONIC` и `TONCENTER_API_KEY` (обе пары кошельков к тому же
удаляются из `process.env` в начале любой команды, `serviceEnv.ts`). Сторож прувера запускается своей группой процессов (`detached`): отмена,
сигнал и выход сервиса шлют SIGTERM/SIGKILL всей группе — прувер и всё, что запустил сторож, не
остаются сиротами; оставшимся в группе после выхода сторожа — SIGKILL. Обработчики `exit`
(дочернего и процесса) не бросают (круг 22, 3): сбой kill (EPERM и др.) — строка журнала
«дочерние процессы: … не удался», дальше проверить руками (`pgrep -g <pid>`).

### Свидетель для блока до головы

Проверено на reth v2.2.0: блок, переданный `engine_newPayloadV3`, но не ставший каноническим,
через RPC **не виден** — `eth_getBlockByHash`, `eth_getBlockByNumber`, `eth_getBlockReceipts`
дают `null`, `debug_executionWitness` и `debug_executionWitnessByBlockHash` — «block not found»,
`testing_buildBlockV1` на нём как на родителе — тоже. rsp берёт блок по номеру. Откатить голову
к предку `forkchoiceUpdated` не может — ни так, ни с `--engine.allow-unwind-canonical-header`
(голова остаётся прежней); а перейти на соседа той же высоты — может.

Выбранный порядок: `newPayload` → `forkchoiceUpdated(head = кандидат, safe и finalized —
прежние)` → свидетель и программа → `forkchoiceUpdated(head = safe = кандидат)`. Голова узла,
таким образом, временно стоит на непроверенном блоке; то, что правило «головой — только после
программы» защищает, держится иначе: следующий блок строится только от **проверенной** вершины
сервиса, safe и finalized двигаются только после проверки (finalized — после приёма батча,
PROTOCOL-V2.md, 0.3), батч и задание пруверу есть только у проверенного блока, а отвергнутого
кандидата вытесняет следующий кандидат той же высоты. RPC узла наружу не открыт: его временную
голову никто, кроме сервиса, не видит.

Вернуть голову на проверенную вершину нельзя (проверено на reth v2.2.0): `forkchoiceUpdated` с
головой-предком отвечает VALID и не меняет **ничего** — ни голову, ни safe, ни finalized; `debug_setHead`
отвечает null и ничего не делает. Поэтому, если после отказа (или выброшенного устаревшего
кандидата) собирать нечего, шаг возвращает `{ kind: 'idle', unverifiedHead }` и пишет об этом в
журнал; safe и finalized к этому времени уже на проверенном, голову вытеснит следующий кандидат.
Голова, к которой не откатиться, менять safe/finalized тоже не даёт: их сервис двигает только
вызовами, где голова — сам кандидат или нынешняя голова.

### Состояние и перезапуск

`state.json` (запись — временный файл, fsync файла, переименование, fsync каталога): вершина
(номер, хеш, время, отметка и курсор очереди, фронтир и счётчик дерева выводов, отчёт хоста), последний принятый батч,
кандидат в работе с фазой (`built` → `inserted` → `tentative`), блоки со статусом
(`checked` → `proven` → `accepted`; у непринятого — родитель, отрезок и отметка `submitting`),
пересборка в работе (`rebuild`), начало отставания очереди (`queueLagSince`), журнал отказов.
Файлы каталога блока (`report.json`, `batch.bin`, `payload.json`, `job.json`) пишутся так же. Перезапуск продолжает кандидата с его фазы —
из сохранённого ответа узла, без новой сборки (у новой было бы другое время и другой хеш); но
кандидат старше `staleCandidateAge` выбрасывается и собирается заново (его батч мог бы не успеть
к контракту), прежнего вытесняет новый той же высоты. Узел, перезапущенный после `newPayload`
(неканонический кандидат живёт у него только в памяти), на временную голову отвечает не VALID:
фаза откатывается к `built`, и кандидат отдаётся узлу заново из сохранённого ответа.
Узел пишет канонические блоки на диск сразу (`--engine.persistence-threshold 0`); если он
потерял блоки, сервис отдаёт их заново из `blocks/<N>/payload.json`. Журнал —
`stateDir/sequencer.log`.

## Прувер (`prover.ts`, `proofImport.ts`)

`LocalProver` — очередь на диске `.tools/sequencer/proofs/<ключ задания>/` (`job.json`,
`status.json`, `proof-raw.json`, `fixture/`, `prove.log`, `proof.json`), строго одно задание за раз.
Запуск — `zkvm-evm/host/prove-guarded.sh --batch-input <batch.bin> --prove --proof-out <файл>` с
переменными шардов из `zkvm-evm/host/prover-shards.env` (тот же файл — в PROVING.md и для этапов на
процессоре в `remote/measure.sh`). Коды сторожа: 95 (другой прувер работает) — ждать; 98 (мало места
для старта) — тревога в журнал и ждать (всего не дольше 2 ч); 99 (место кончилось) и 94 (вышло время) —
повтор, по умолчанию один; прочие — отказ (`ProverFailure`). `cancel` гасит сторожа (SIGTERM, через
15 с — SIGKILL) и помечает задание `cancelled`. После пруфа — импорт и сверка: файл пруфа против
задания и `program.json` (публичные значения, ключ программы, ELF), `zk/import-sp1-fixture.mjs …
sp1_evm_sequencer --out-dir <каталог задания>/fixture --report <report.json>` (проверка спариванием,
публичные значения против отчёта блока; `fixtures/` не трогается), `zk/gen-bn254-groth16-fixture.mjs
--dir`, затем публичный вход и ключ контракта (`key.json`). Не прошёл — `ProofRejected`, повтора нет.
Проверенный пруф переживает перезапуск. `RemoteProver` — заготовка с тем же договором (ssh/scp на
сервер с GPU по скриптам `zkvm-evm/host/remote/`), с настоящим сервером не запускалась.

## Сервис против контракта в testnet

Контракт разворачивает сам сервис: `npx ts-node sequencer/main.ts deploy [--escape-timeout=21600]
[--max-block-age=3600] [--proof-time=1800] [--state-dir=…] [--chain-id=<число>] [--dry-run]`
(`deploy.ts`) — владелец и секвенсор — кошелёк сервиса; chainId — свой у развёртывания
(`chainId.ts`: `--chain-id` или случайный 40-битный, не 362107787851 и не из
`bench/testnet-run-*.json`, не Linea, не больше 2^53 − 1; записан в `<state-dir>/deploy-chain.json`
до первой отправки и при `--dry-run`, повтор берёт его же, другой `--chain-id` — отказ); генезис —
протокола (`GENESIS_HASH` от chainId не зависит: chainId есть только в config узла; программа берёт
chainId из входа и коммитит словом 0, контракт хранит свой — круг 23, пункт 2); ключ — `key.json` частями и
`FinalizeKey`, сообщения — тем же `TestnetSubmitter` (журнал, монотонные снимки; новые следствия
`deployed`, `keyPart`, `keyHash`), в конце — сверка развёртывания (`rollupDeployment.ts`) и команды
`check`/`run`. Адрес печатается до первой отправки; активный контракт по адресу с другим состоянием
(владелец, секвенсор, параметры, код, другой ключ) — отказ; начатое развёртывание продолжается;
`state.json` в каталоге при новом развёртывании — отказ (каталог от прежнего контракта). `address` —
адрес кошелька сервиса без сети. Запись журнала `outbox.json` теперь несёт адрес контракта: запись
для другого контракта — отказ доводить её этим. `maxBlockAge` контракта — не меньше `300 +
expectedProofTime + 300` (с пруфом 1800 с — от 2401 с); по умолчанию 3600. Суточный прогон —
TESTNET.md, «Секвенсор как сервис».

Окружение (`serviceEnv.ts`, круг 23, пункт 1): `SEQUENCER_MNEMONIC` и `SEQUENCER_WALLET_VERSION`
(`v4` или `v5r1`; по желанию `SEQUENCER_WALLET_ID` / `SEQUENCER_SUBWALLET_NUMBER`) — кошелёк
сервиса, и ТОЛЬКО он; `WALLET_MNEMONIC` / `WALLET_VERSION` — кошелёк прогонов (Blueprint,
нагрузка), сервис его не берёт. Обе пары лежат в `.env` проекта: сервис читает его сам (dotenv
`parse`, без печати и без переноса всего файла в окружение; переменная окружения процесса главнее
строки файла) в начале любой команды и сразу удаляет обе пары из `process.env`. Тот же ключ в
`SEQUENCER_MNEMONIC` и `WALLET_MNEMONIC` — отказ «кошелёк сервиса совпадает с кошельком прогонов».
Ни отдельного файла окружения, ни `set -a` не нужно. Ключ живёт только в памяти, не печатается и не
пишется на диск. **Рекомендуется `SEQUENCER_WALLET_VERSION=v5r1`** (подпись v5r1 привязана к сети,
`global_id`); на v4 `check` предупреждает. Баланс кошелька сервиса держать малым (на несколько
десятков батчей) и пополнять по мере расхода. Мнемоника из `.env` в исходное окружение процесса
не попадает; заданная переменной окружения — попадает, и `ps eww <pid>` её показывает процессам
того же пользователя и root (удаление из `process.env` закрывает её только от дочерних). Поэтому
— в `.env`, а не в командной строке. `TONCENTER_API_KEY` — по желанию, из того же `.env` (без него 1 запрос в секунду). Сеть — только
`testnet.toncenter.com`, и ещё сверяется `global_id` (−3). Бинарники — как выше, хост с прувером
(`--features native-gnark`), артефакты схемы Groth16 в `~/.sp1/circuits/groth16/v6.1.0`, 20+ ГБ
свободного места; тяжёлое на машине во время пруфа не запускать.

Запускать `run` в `tmux` (или под launchd), а не прямо в окне терминала: сторож прувера — своя
группа процессов, и SIGHUP при закрытии терминала до неё не доходит. Сервис по SIGHUP гасит
группу сам, но если его убьют без сигнала (SIGKILL, падение терминала), прувер останется сиротой
— тогда `pgrep -f prove-guarded` и погасить руками.

```bash
npx ts-node sequencer/main.ts check <адрес> --fee-recipient=0x<адрес L2 секвенсора>   # ничего не шлёт
npx ts-node sequencer/main.ts run <адрес> --fee-recipient=0x… [--proof-time=1800] [--poll=30]
```

`check`: сеть (testnet), контракт (секвенсор — этот кошелёк, ключ контракта = `key.json`, генезис,
версия протокола, не заморожен, `maxBlockAge` и бюджет времени), часы против L1, баланс кошелька,
`gen-evm-rollup-key --check`, хост против `program.json`, сторож и файл шардов, артефакты схемы,
место на диске; затем поднимает и гасит узел (под блокировкой каталога — при работающем сервисе
отказывает). `run`: те же проверки, узел reth, очередь toncenter, `LocalProver`, `TestnetSubmitter`, шаги в
цикле (пауза `--poll` при `waiting`/`idle`).

**Кошелёк.** Батч стоит около 0,09 TON (`SubmitBatch` 0,072, порции данных по 0,001, комиссии);
меньше 0,2 TON — отказ, рекомендуется от 1 TON (около десяти батчей). Отправщик: снимок счёта rollup'а
и get-методы на нём (локальный эмулятор TVM — тот же код на тех же данных, одно время), суммы — из
`wrappers/rollupValues.ts`, ожидание — по состоянию кошелька и контракта, не по таймеру. Исходящий
журнал `stateDir/outbox.json` пишется **до** отправки (seqno, срок `validUntil` = время L1 + 120 с,
ожидаемое следствие): после сбоя новое сообщение не шлётся, пока не ясно, принял ли кошелёк прежнее
(seqno вырос — ждать его следствия у контракта) или срок истёк (время L1 позже `validUntil` +
`expiryMargin` (60 с) при прежнем seqno — не дошло, слать снова; запас — от отстающего сервера).

Снимки toncenter монотонны (круг 21, 1): за балансировщиком следующий ответ может прийти от
отстающего сервера — с прежним seqno кошелька и прежним хешем данных, и без защиты это дало бы
дубль порции или сообщение с негодным seqno. Отправщик помнит по каждому адресу наибольшее
`sync_utime` и наибольший lt последней транзакции счёта (круг 22, 1: в пределах секунды отстающий
сервер отвечает тем же `sync_utime`, отличает его только lt) — в процессе и в `stateDir/l1-seen.json`
(`{ "<адрес>": { "utime": …, "lt": "…" } }`, переживает перезапуск); снимок старее по времени или
по lt перечитывается (до 20 раз с паузой опроса, затем `StaleSnapshot`). Следствие, только что
увиденное при разборе журнала, повторно по новому снимку не проверяется. Снимок со временем позже
часов машины больше чем на 600 с (`maxFutureSkew`) — сбой шага, в `l1-seen.json` не пишется (круг
22, 2): иначе одно такое время закрыло бы все честные снимки.

**Если `l1-seen.json` испорчен** (сервис отказывает строкой «l1-seen.json: не таблица…» или
останавливается «снимки toncenter отстают … подряд», а в обозревателе контракт и кошелёк
двигаются): остановить сервис, посмотреть файл и сравнить `utime` с `date +%s` и lt — с lt
последней транзакции счёта в обозревателе. Запись из будущего или больше настоящего lt — ошибка;
удалить файл целиком (`outbox.json` при этом НЕ трогать: он держит защиту от дубля сообщения),
подождать минуту, чтобы серверы toncenter догнали сеть, и запустить `run` снова — таблица
наберётся с первых снимков.

Отказ контракта сообщению, которое кошелёк принял (например, `SubmitBatch` после срока), виден по
транзакции контракта (toncenter `getTransactions`: входящее от кошелька с тем же телом, не раньше
отправки, код выхода) — сразу, строкой «контракт отверг сообщение «…» (код N)», а не через 5 минут
ожидания следствия.

**Остановка.** Код 2 и строка «ОСТАНОВКА: …» — нужен человек: причина в строке и в
`stateDir/sequencer.log`. Так кончаются `SequencerStop` (и при старте), сбой и отмена прувера,
негодный пруф (`ProofRejected`: повтор построил бы его заново тем же входом) и чужая блокировка
каталога (`StateDirBusy`: работает второй экземпляр) — без повторов. Сбой сети и индексатора
повторяется (десять подряд — остановка). Отстающие снимки (`StaleSnapshot`) считаются отдельно, по
времени: подряд дольше `staleLimitSeconds` (30 мин) — остановка (круг 22, 4). Сигнал во время шага
— код 1 и строка «прервано по сигналу …», что бы ни бросил прерванный шаг (импорт пруфа, погашенный
сигналом, отвечает отказом — это не негодный пруф). Сначала
`check`; затем, если причина устранена, `run` снова — он продолжит с записанного состояния (блок,
пруф, исходящий журнал). Ctrl-C — дочерние гасятся, второй Ctrl-C — сразу. Батч, не принятый за
`maxBlockAge`, сервис пересобирает сам; если очередь L1 ждёт дольше `escapeTimeout`, rollup может
заморозить кто угодно — тогда путь только аварийный (`scripts/runRethCycleTestnet.ts escape`).

## Чего нет

- Запуска в testnet: прувер, отправщик и `deploy` проверены только в Sandbox и на заглушке сторожа
  (порядок суточного прогона и нагрузка `scripts/sequencerTraffic.ts` — TESTNET.md).
  Впервые в сети исполнятся: toncenter (`getAddressInformation`, `sendFile`, `getConfigParam`, 429),
  `sync_utime` за балансировщиком, настоящий кошелёк и его комиссии, время блоков L1, настоящий
  пруф через сторожа (15 минут, своп) и цикл `run`. `RemoteProver` — без сервера.
- Конвейера: следующий блок собирается после приёма батча предыдущего. Несколько блоков в
  батче — нет (это смена программы).
- Предела числа пересборок одной высоты: если пруф всегда дольше `expectedProofTime`, блок
  пересобирается снова и снова (каждый раз — строка журнала).
- Хранения и ротации ключа секвенсора: мнемоника — в переменной окружения.
