### 0.1. Принудительной может быть только транзакция вывода через мост

Ошибка проекта (CRITICAL): плата за элемент очереди бралась за штуку, а «вес» элемента для
прувера доходил до миллиона газа произвольного кода (`blake2f` — 1 gas за раунд, программно:
порядка 10⁹ циклов на транзакцию). Секвенсор обязан включить такую транзакцию, доказать её за
срок не может — rollup замораживается за 0,05 TON. Понижение предела газа не спасает.

Решение для этой смены — узкий класс с известной ценой:

- принудительная транзакция действительна по форме, только если `to == BRIDGE_ADDRESS`,
  `gas_limit ≤ FORCED_TX_GAS_CAP`, тип 0/1/2, свой `chainId`, это не создание контракта и
  `encoded_2718(tx)` побайтно равен байтам из очереди (иначе — пропуск; сравнение с транзакцией
  блока — тоже по байтам, а не по кешированным хешам);
- исполняется при этом только код моста (раздел 7): ни прекомпиляций, ни чужого кода. Цена для
  прувера — восстановление подписи, проверки revm и ~1,8 тыс. gas кода моста;
- что это гарантирует: пользователь обычного счёта всегда может вывести свои монеты в обход
  секвенсора. Чего не гарантирует: принудительный вызов произвольного контракта и принудительный
  перевод. Они — отдельной сменой, с объявленным газом в элементе очереди, платой по газу и
  бюджетом газа на блок, после замера худшего числа циклов на gas (ROADMAP, этап 3);
- `FORCED_TX_GAS_CAP` — небольшой запас над расходом вызова моста (21 000 + данные + код моста);
  точное значение — после замера в спайке 4, ориентир 40 000;
- ошибка «не помещается по газу блока» для принудительных становится недостижимой при
  `K × FORCED_TX_GAS_CAP ≤ GAS_LIMIT` (K — из 0.2) и остаётся ошибкой батча как защита в глубину;
- мост-предустановка поэтому обязателен в этой смене.

### 0.2. Обязательность — по сроку заморозки, отрезок ограничен числом элементов

- `inclusionDelay` и правило возраста элемента N+1 из раздела 5 — УБРАНЫ: к заморозке они
  добавляли мало, а давали новый режим отказа («после простоя весь просроченный хвост — одним
  блоком»). Цензуру ограничивает заморозка, как сейчас: самый старый необработанный элемент
  старше `escapeTimeout` — rollup замораживает кто угодно;
- батч обрабатывает любой префикс: `processed ≤ N ≤ head`. Контракт дополнительно требует
  `N − processed ≤ MAX_BATCH_QUEUE_ITEMS` (то же проверяет программа числом элементов отрезка):
  секвенсора нельзя заставить взять в блок больше, а сам он больше взять не может — значит цена
  пруфа батча ограничена сверху известным числом;
- `oldestPendingAt` не хранится: это `queueItems[processed + 1].queuedAt`;
- `MAX_BATCH_QUEUE_ITEMS` и нижняя граница `escapeTimeout` выводятся из замера (спайк 4): время
  пруфа блока с `MAX_BATCH_QUEUE_ITEMS` принудительными выводами и сколько таких батчей нужно,
  чтобы разобрать очередь, которую плата за место ещё позволяет создать. До замера константы в
  ELF не фиксируются;
- открытый вопрос К-4/5-1 (можно ли купить заморозку спамом) этим НЕ закрыт, а сведён к одному
  числу: пропускная способность прувера в элементах за срок против цены очереди такой длины.
  Число и вывод записываются в ARCHITECTURE после замера.

### 0.3. Время блока

`now − MAX_BLOCK_AGE ≤ blockTimestamp ≤ now`; `MAX_BLOCK_AGE` — параметр развёртывания, границы
проверяются в `FinalizeKey` (не меньше получаса, не больше `escapeTimeout`). С `inclusionDelay`
он больше не связан. Последствие, которое надо записать: батч, не принятый за `MAX_BLOCK_AGE`,
негоден навсегда — блок L2 и всё, что на нём построено, пересобирается; сборщик двигает
финальность только после приёма батча.

### 0.6. Правки по итогам реализации и круга 15 (главнее текста ниже)

- **Предел длины принудительной транзакции — 256 байт**, и в программе (`FORCED_TX_MAX_BYTES`:
  длиннее — пропуск без разбора), и в контракте (`MAX_FORCED_TX_BYTES = 256`,

  не поместится, и кошелёк обязан это проверять. Слова «в программе нет предела длины»
  (раздел 3) и «64 ячейки» (разделы 2, 3 и 11) недействительны.
- **Причин пропуска по исполнению восемь, а не шесть**: добавлены `NonceOverflow`
  (nonce = 2⁶⁴−1) и `PaymentOverflow` (переполнение `value + gas·price`). Обе достижимы
  одними байтами элемента, и как ошибка батча каждая была бы выключателем.
- Событие моста — `Withdrawal(address,bytes32,uint256)` (правка 0.4), а не как в разделе 5.
- Счётчик выводов — не больше 2³²−1.
- Лог моста: дополнительно требуются нулевые старшие 12 байт топика отправителя и сумма в
  пределах u128.
- `FORCE_TRANSACTION_STEP_GAS = 50 000` (измерено 36 303 на глубокой вставке).

## 1. Краткий итог решений

1. **Принудительные транзакции EVM.** Элемент очереди — `sha256(prev ‖ MARKER ‖ keccak256(сырые байты транзакции))`. Байты приходят «змейкой» ячеек, хеш считается из прочитанных битов. В блоке принудительные идут первыми, в порядке очереди. Признак «некорректна» — отказ самого revm на состоянии в этот момент (`InvalidTransaction`), а не переписанные правила.
2. **Дерево выводов** — фронтир из 32 хешей и счётчик. Счётчик обязателен в публичных значениях: корень его не связывает (атака в разделе 4).
3. **Очередь.** Отметка `target` исчезает. Батч заявляет `queueProcessedUpTo = N`; контракт берёт хеш в точке N из словаря элементов очереди. Обязательность — по возрасту первого необработанного элемента.
4. **Время.** Слово `blockTimestamp`; контракт требует `now − MAX_BLOCK_AGE ≤ ts ≤ now`.
5. **Мост.** Предустановка в генезисе, выводы по логам, хеш кода проверяется программой, когда в блоке есть лог моста. Рекомендую делать сейчас: позже это новый генезис.
6. **Заголовок.** Закрепить лимит газа, `PREVRANDAO = 0`, пустой `extraData`, нулевой корень beacon-блока. Получатель чаевых остаётся свободным.
7. **Контракт v2 — только EVM.** `ForceExit`, `SetExitKey` и ключ выхода убираются: программы выхода для EVM нет, а ключ-заглушка хуже отсутствия пути.
8. **Игрушечный реестр — заморозить как исторический** на теге нынешнего коммита (`654df0b`). `zkvm/` не трогать, пруфы не перестраивать.
9. **Все девять нынешних пруфов SP1 к контракту v2 не подходят** (5 игрушечных, 4 EVM): меняется дайджест.
10. **Несколько блоков в батче — отложить.** Формат публичных значений от числа блоков не зависит.

### (б) Формат

- `ForceTransaction { queryId:u64, l2Transaction: cell }`. Ячейка — «змейка»: целые байты, не больше одной ссылки, не больше `MAX_FORCED_TX_CELLS = 64` ячеек (до 8 128 байт). Резать можно где угодно.
- Элемент очереди: `headHash' = sha256(headHash ‖ 1<<255 ‖ keccak256(байты))`.
- Байты — подписанная транзакция в кодировке EIP-2718. Второе слово элемента тогда равно хешу транзакции Ethereum.
- Раскладку `dataChunkCell` не переиспользовать. Она потребовала бы проверки формы дерева в TVM, и любая принятая форма, которую программа не воспроизведёт, — снова выключатель. Хеш прочитанных битов закрывает находку 3 (ссылка на библиотеку) по построению.
- Плата — прежняя, плоская (от 0,05 TON с удвоениями). `FORCE_TRANSACTION_STEP_GAS` поднять: ~250 gas на ячейку (предположение), замерить на 64 ячейках.

### (в) Правила программы

Отрезок очереди батча — элементы `(processed, N]`. Депозиты отрезка обязаны совпасть с зачислениями блока, как сейчас. Принудительные обрабатываются до транзакций секвенсора:

1. Не разобралась `decode_2718_exact`, тип вне 0/1/2, нет `chainId` или он чужой, подпись не восстанавливается тем же `recover_signer`, что у блока, `gas_limit > FORCED_TX_GAS_CAP` → **пропуск**.
2. Иначе `executor.execute_transaction_without_commit(tx)` на живом состоянии:
   - `Ok` → следующая транзакция блока обязана иметь тот же хеш, иначе ошибка батча (секвенсор цензурирует). Затем `commit_transaction`.
   - `Err(Validation(InvalidTx))` → **пропуск**. Это nonce, баланс на `gas_limit × maxFee + value`, код у отправителя (EIP-3607), цена ниже базовой комиссии, intrinsic gas.
   - `Err(TransactionGasLimitMoreThanAvailableBlockGas)` → **ошибка батча**, не пропуск: секвенсор обязан закончить отрезок раньше. Иначе тяжёлые элементы перед жертвой выдавливали бы её. Первой в блоке транзакция с `gas_limit ≤ CAP ≤ GAS_LIMIT` помещается всегда.
   - Любая другая ошибка → ошибка батча.
3. Остальные транзакции блока — `execute_transaction`, затем `apply_post_execution_changes` и прежние сверки.

Цикл собирается из тех же частей, что `execute_one` (reth `crates/evm/evm/src/execute.rs:552-566`): `State::builder().with_database(db).with_bundle_update()`, `evm_config.executor_for_block`, `apply_pre_execution_changes`, в конце `merge_transitions`.

**Почему это корректно.**

- Признак «некорректна» вычисляет тот же код, которым Reth решает, включать ли транзакцию: alloy-evm `eth/block.rs:160-206`, revm `validation.rs:120-236`, `pre_execution.rs:84-120, 126-161`. Расхождение «программа считает корректной, а узел включить не может» невозможно по построению. Именно оно вернуло бы выключатель.
- Состояние «в этот момент» — после предыдущих включённых принудительных, до транзакций секвенсора. Это ровно то, что запрошено.
- Спрятать свидетеля, чтобы выдать счёт за пустой, нельзя: нераскрытый узел — паника (`vendor/rsp-mpt/src/lib.rs:476`, `.unwrap()` на `NodeNotResolved`), пруфа нет.
- Ошибка проверки в revm возникает до изменения счёта (`validate_against_state_and_deduct_caller`), журнал сбрасывается в `catch_error` (`handler.rs:525-532`). Что после отказа не остаётся следа в `State` — **предположение**, закрепить тестом корня состояния.

**Принцип.** Ни одно свойство элемента очереди, которое контракт не проверяет, не может быть ошибкой батча. В программе нет предела длины принудительной транзакции.

**Семантика, которую надо записать в документы.**

- Зачисления EIP-4895 применяются в конце блока. Принудительная транзакция видит депозиты только предыдущих батчей; «депозит и сразу транзакция с него» в одном отрезке будет пропущена.
- Пропуск по цене ниже базовой комиссии остаётся рычагом: секвенсор может поднять базовую комиссию, сжигая свои монеты. Пользователю — ставить `maxFeePerGas` с запасом.

### (б) Формат

- `DepositQueue { headCount:u64, headHash:u256, processedCount:u64, processedHash:u256 }`.
- `RollupState.queueItems: map<uint64, QueueEntry>` на месте `depositReceipts`. Свободных ссылок у `RollupState` нет: четыре из четырёх заняты.
- `QueueEntry { hashBefore:u256, queuedAt:u32, receipt: DepositReceipt? }`. Ключ — номер элемента с единицы, `hashBefore` — хеш очереди до него. Не больше ~680 бит, один лист.

- `RollupStorage.inclusionDelay:u32` либо производная от `escapeTimeout`.

### (в) Правила контракта

- `pushQueueItem`: запись `queueItems[head+1] = {headHash, now, квитанция}`. Если очередь была обработана целиком — `oldestPendingAt = now`. Попутно удалить до двух записей с ключом `≤ processedCount`.
- `prepareSubmitBatch`: `processedCount ≤ N ≤ headCount`, иначе новый код. Если `N == head`, то `newDepositHash = headHash`. Иначе `e = queueItems[N+1]`, `newDepositHash = e.hashBefore`, и `now − e.queuedAt ≤ inclusionDelay` (новый код «очередь просрочена»).
- `applyBatch`: `processed = (N, newDepositHash)`, `oldestPendingAt = (N == head) ? 0 : e.queuedAt`. Удалять записи в `SubmitBatch` нельзя по газу.
- Заморозка: по `oldestPendingAt`, как сейчас.
- Плата: окно равно `headCount − processedCount`, то есть незавершённый хвост, а не «с прошлого батча».
- `CancelDeposit`: запись `> processedCount` с квитанцией, удаляется целиком.

**Что это даёт.** Элемент может обработать ближайший батч (снимает 3-К4: «два пруфа подряд»). Блок, собранный до прихода депозита, остаётся годным. Раздутое окно можно обрабатывать частями. Срок годности батча известен заранее: если блок обработал очередь до головы на момент сборки `T`, батч годен до `T + inclusionDelay`, и посторонний это ухудшить не может.

### (д) Тесты и мутации

- N меньше `processed`, больше `head`, равно `processed` (пустой отрезок), посередине, равно `head`.
- Граница возраста: ровно `inclusionDelay` проходит, на секунду больше — отказ.
- Заморозка после частичной обработки; `oldestPendingAt` на всех переходах.
- Депозит между сборкой блока и приёмом батча не ломает батч (сам сценарий 6-Г).
- Уборка не трогает необработанное; возврат депозита после заморозки.
- Плата по новому окну: перепроверить набор 5-7.
- Мутации: каждое сравнение; `hashBefore` против «хеша после»; `N+1` против `N`.

### (е) Риски и альтернативы

- Батч, опоздавший за `inclusionDelay`, отклоняется, и блок L2 под ним придётся пересобирать. Сборщик двигает финальность только после приёма (уже записано в 11-2).
