# Спайк: один Groth16 на несколько блоков EVM (агрегация SP1)

**Это измерение, не внедрение.** Протокол v2, программа EVM (`zkvm-evm/lib`, `program`, `vendor`),
контракт, ключи и фикстуры не менялись: ELF программы EVM `6828d42b…7d05fba3`, `programVKey`
`0x0044524c…b239d94d`, `keyHash` `0x2330523d…cf7cc62c`, `sourcesSha256` `41956908…d50643db` —
прежние (`gen-evm-rollup-key.mjs --check` сходится, `tests/ProgramBinding.spec.ts` проходит).
Спайк — своё рабочее пространство cargo, не член `zkvm-evm/Cargo.toml`, и в хеш исходников
программы не входит. Агрегатный пруф к контракту не подключён. Все цифры — `bench/aggregation-spike.json`
(собирает `ton/write-bench.py` из файлов замера, только измеренное).

## Гость-агрегатор

Вход: дайджест ключа программы EVM (`[u32; 8]`), N, затем N раз 352 байта публичных значений блока;
сжатые пруфы блоков хост кладёт в поток отложенных пруфов (`SP1Stdin::write_proof(proof, vk.vk)`).

- `sp1_zkvm::lib::verify::verify_sp1_proof(&[u32; 8], &[u8; 32])` — фича `verify` у `sp1-zkvm` И
  `sp1-lib` (`sp1-lib-6.10.0/src/verify.rs`); дайджест публичных значений — sha256, как у `commit_slice`.
  Исполнитель только копит дайджест отложенных пруфов, сами пруфы проверяет рекурсия при сжатии.
- Ключ программы EVM — **константа в ELF агрегатора** (`EVM_PROGRAM_VKEY`), вход с ней сверяется:
  иначе агрегатор принял бы пруфы любой программы. 8 слов получены обратным разложением
  `programVKey` (это Σ wᵢ·2^(31·(7−i)), слова меньше 2³¹ — `koalabears_to_bn254` в sp1-hypercube);
  хост сверяет их с `hash_u32()` ключа, который SDK выводит из ELF EVM, а `bytes32` — с program.json.
- Сцепка соседей: `chainId` равен; `prevStateRoot`, `prevWithdrawalsRoot`, `prevDepositHash`,
  `prevWithdrawalsCount` блока i+1 равны новым словам блока i; время не убывает.
- Наружу (набросок, не протокол): `chainId`, prev* первого блока, new* последнего, `blockTimestamp`
  последнего, `batchHash` = sha256(batchHash₁ ‖ … ‖ batchHash_N).

## Замеры (сервер zk-gpu: 2× RTX A6000 48 ГБ, 48 потоков, 377 ГБ ОЗУ)

Цепочка Reth (`fixtures/evm_batches/reth`), блоки 1–8 подряд, ключ программы EVM — нынешний.
Каждый агрегатный пруф проверен локально SDK, на маке — спариванием под закреплённым ключом схемы
v6.1.0, его 11 слов совпали с посчитанными из `block-N.json` мака.

**Сжатый пруф блока** (GPU, сам пруф, без подъёма процесса): 9,3–14,3 с, в среднем 11,2 с
(тёплый процесс, `pipeline.sh`); пик видеопамяти 23,4–24,4 ГБ. Холодный процесс на блок — 71–89 с:
из них 38–85 с уходит на сверку ключа ELF на процессоре и ~20 с на подъём сервера GPU.

**Агрегат** (одна карта, процесс на N): циклы агрегатора 1,34 / 1,43 / 1,52 / 1,89 млн при
N = 2 / 3 / 4 / 8 (≈ 1,16 млн + 92 тыс. на блок — меньше 2% циклов одного блока EVM); сжатый агрегат
2,5–4,2 с; Groth16 агрегата одним запросом 88–97 с независимо от N, из них gnark на процессоре
(`acceleration=none`): чтение R1CS 26–32 с, ключа 6 с, пруф 41–46 с. Тёплый Groth16 (второй в том же
процессе, N = 8) — 53,4 с. Видеопамять 12,2–13,3 ГБ, занятая ОЗУ машины до 61,9 ГБ (в покое 30,2).

| N | сжатые пруфы блоков, Σ (тёплые, 1 карта) | агрегат: процесс целиком (холодный) | итого на блок, 1 карта | газ проверки на TON на блок |
|---|---|---|---|---|
| 1 (нынешний путь) | — | — | 178 с холодный Groth16 блока 3; ~62 с тёплый (блок 7) | ~950 тыс. |
| 2 | 19,3 с | 114,9 с | 67,1 с | 475 тыс. |
| 3 | 30,4 с | 123,9 с | 51,4 с | 317 тыс. |
| 4 | 41,3 с | 114,2 с | 38,9 с | 238 тыс. |
| 8 | 89,9 с | 124,3 с (тёплый: Groth16 53,4 с + проверка пруфов блоков и исполнение 2,3 с) | 26,8 с (тёплый агрегат: 18,2 с) | 119 тыс. |

«Итого на блок» = (Σ сжатых + процесс агрегата) / N. Нынешний путь — `bench/remote-gpu-proof.json`
(блок 3 в одиночку 178 с; тёплый прувер, блок 7: 62–63 с). Газ на блок = 950 тыс. / N: это цена одной
проверки пруфа, логика rollup-контракта на N блоков (N хешей данных и т. п.) не мерилась.

**Две карты, тёплый конвейер N = 8** (`pipeline.sh`): сжатые пруфы 1–4 и 5–8 на двух картах — 84 с
стенных (вместе с подъёмом ключа ~20–25 с на процесс), агрегат — 125 с (178 с минус второй, замерный
Groth16): ~209 с на 8 блоков, ~26 с на блок. Из замеренных частей в установившемся режиме (без подъёма
процессов): 8 × 11,2 с / 2 карты + 53,4 с ≈ 98 с на 8 блоков, ~12 с на блок — **оценка**, такой
режим целиком не мерился.

**Газ на TON** (`ton/verify-gas.ts`, общий верификатор BN254 в Sandbox): пруф блока 3 — 945 622,
агрегаты N = 2 / 3 / 4 / 8 — 947 490 / 938 389 / 944 814 / 945 232; лучшая подделка каждого — код 7100.
Пруф того же вида (верификатор SP1 v6.1.0, 5 публичных входов), газ одинаков в пределах разброса от
битов дайджеста. Импорт через `zk/import-sp1-fixture.mjs` невозможен (он сверяет ключ с program.json
EVM), поэтому проверка повторена скриптом спайка; `zk/gen-bn254-groth16-fixture.mjs --dir` подсказки
строит без правок (каталог вне `fixtures/`).

## Выводы

- **Агрегация стоит включения в следующую смену протокола, при N = 4–8.** Газ проверки на блок
  падает в N раз (при N = 8 — ~119 тыс. вместо ~950 тыс.), время прувера на блок на одной карте — в
  1,6 раза при N = 4 и в 2,3 раза при N = 8 с холодным процессом агрегата (38,9 / 26,8 с против ~62 с
  тёплого Groth16 на блок), в 3,4 раза при N = 8 с тёплым агрегатом (18,2 с).
- Причина — Groth16 (gnark на процессоре, ~42–46 с, и ~34 с чтения схемы в холодном процессе)
  платится раз на агрегат; стоимость агрегата от N почти не зависит (88–97 с при N = 2…8), рекурсия
  N пруфов на GPU — секунды. N = 2 даёт мало (67 с на блок в холодном процессе); выгоднее держать
  прувер тёплым — один процесс на карту, это даёт больше, чем сама агрегация при малых N.
- Сжатый пруф блока — 9–14 с на GPU: две карты перестают быть узким местом, узким местом становится
  gnark на процессоре (одно задание агрегата за раз на машину).

## Что нужно для внедрения (смена протокола)

Что контракт должен был бы проверять и чего в наброске нет:

1. **Ключ.** В ключ контракта (IC0) входит ключ агрегатора, а не программы EVM. Ключ программы EVM
   зашит в ELF агрегатора: любая правка программы EVM меняет оба ELF и оба ключа; цепочку привязки
   (`PROVING.md`: исходники → program.json → key.json) надо продлить на агрегатор (свой хеш исходников,
   `verify-elf`, `--check`).
2. **Данные каждого блока.** Сейчас `batchHash` берётся из `pendingData` одного блока. Для агрегата
   контракт должен хранить N хешей данных (или их сцепку в порядке блоков) и сверять с
   sha256(batchHash₁ ‖ … ‖ batchHash_N) — тот же расчёт в контракте, в программе и в
   `wrappers/rollupMath.ts`; рост `pendingData` и газа приёма не мерился.
3. **Отметка очереди.** Достаточно одной — конечной: prevDepositHash первого и newDepositHash
   последнего блока, контракт берёт хеш в точке N у себя, как сейчас. Но предел элементов на батч
   (`MAX_BATCH_QUEUE_ITEMS = 32`) становится 32·N (каждый блок программы — по-прежнему ≤ 32), и
   словарь очереди должен держать отметку на столько вперёд.
4. **Время каждого блока против `maxBlockAge`.** В наброске наружу идёт время последнего блока, а
   окно `maxBlockAge` должно действовать на ПЕРВЫЙ (самый старый) блок: нужно 12-е слово (время
   первого блока) или правило в агрегаторе «время блоков в окне ≤ X». Агрегат дольше ждёт N блоков —
   задержка до приёма растёт на время сборки N блоков; `maxBlockAge` и срок заморозки сверять с этим.
5. **Переменное N.** Ключ один на любые N в 1..MAX (агрегатор так и написан); N = 1 — запасной путь,
   когда агрегат большой не собирается. Выводы — конечные корень и счётчик, хватает как есть.
6. **Формат публичных значений** — 11 слов остаются 11 (или 12 со временем первого блока); дайджест и
   верификатор те же. Это смена протокола: другой смысл `batchHash` и слов prev/new.

## Риски

- Агрегатор — новый доверенный код. Обязательны: константа ключа программы, sha256 публичных
  значений, проверка отложенных пруфов рекурсией (`deferred_proof_verification(false)` в рабочем
  пути — никогда), сцепка всех пяти пар слов и времени; враждебная проверка и мутации, как у программы.
- Отложенные пруфы годны только той же версии SP1 (корень ключей рекурсии `vkRoot`): блоки и агрегат
  строятся одной версией.
- Сбой одного блока задерживает весь агрегат (запасной путь — меньшее N).
- Подъём сервера GPU нестабилен: 3 из 11 холодных стартов хоста EVM («Could not connect to
  sp1-gpu-server socket») и 1 из 9 стартов хоста спайка («Broken pipe») — помог повтор через 5 с;
  службе нужен тёплый процесс на карту, а не процесс на пруф.
- Сборка ELF агрегатора побайтно не воспроизводима, как и ELF EVM.

## Что не мерилось

N > 8; тёплый агрегат при N = 2, 3, 4 (только N = 8); установившийся конвейер с перекрытием агрегата
и пруфов следующих блоков; газ rollup-контракта с приёмом агрегата (только общий верификатор);
стоимость данных N блоков в сообщениях TON.
